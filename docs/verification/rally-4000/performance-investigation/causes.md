# 原因調査の結論と確度

原因を単一処理へ完全には帰属できていない。実測で確認した大きな要因は、このLinux/SwiftShader環境の描画ピクセル数への依存である。mainから既に重く、PR27の追加描画にも増分がある。CPUの虹色・背景更新や音声を停止しても大きな描画間隔短縮は再現せず、CPU制限だけでも説明できなかった。

A=main aff31169、B=PR27修正前059bcba8、C=採用変更a180f27（最終コードb697a98とsrc同一）。同じ現行runnerで測定し、古い性能記録は数値の比較母集団へ混ぜていない。[環境・ハッシュ](environment.json)、[短期診断](stage1-summary.json)、[正式交互比較](quality-paired-summary.json)、[独立計測レビュー](measurement-review.md)を参照。

GPU相当時間はSwiftShaderの有効な非disjoint非同期query。CPUのrender送信時間、RAF間隔とは別である。CPU計測はwall timeであり、スケジューリング待ちを含み得る。effects内のbackground/rainbow等は包含関係があるため単純合計しない。

D02非表示は更新を継続、D03 live停止は更新と転送が同時に変わる。CPUだけの根拠には、同じ描画入力・転送量を保った別のfrozen対照を使った。初期のpaused/無音/計測初期化不備を含む失敗は保存し、正式改善率には流用していない。

次に必要なのは、ハードウェア描画と実機Safariで同じ入力・warmupの対照を取り、既存sceneの個別pass/材質/overdraw寄与を独立に測ること。標準画質の残存遅延、ピクセル削減後も59秒進まない理由の細分化、端末の熱と入力遅延は未解決。dt・衝突精度・遅延停止条件を変える対策は採っていない。
