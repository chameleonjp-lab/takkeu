# Viewport / direct paddle implementation plan

User specification: 2026-10-23 task in this session, sections 1–10. It explicitly authorizes implementation decisions and Draft PR creation without a new approval gate.

Goal: use the entire browser content viewport, preserve the visible-contact game, and make pointer placement/drag/release agree with the simulation.

Base: `3e7ceba208200db931af645fdae1ccb271f4a7b7`; origin `https://github.com/chameleonjp-lab/takkeu.git`. Fresh clean clone; branch `feat/viewport-direct-paddle`. PR #13 merged at this base; no open PRs. Existing branches inspected; only unmerged tip is an old Pages documentation commit, unrelated. No existing work replaced.

Architecture: keep the common eye/target, reference reach frame, projection/contact rule, geometry, speed/flight/scheduling values and resource guards. First expand layout only. Actual camera-ray intersection maps CSS pixels to z=paddleZ, then clampPaddle. Ordered place/move/release samples are consumed only in uncommitted physics time. No speed limit/sensitivity/easing in direct control. Render the resulting physics snapshot.

Alternatives: absolute rectangle scaling is incorrect for perspective; changing paddleSpeed also changes reservations; render-only movement disagrees with contact. Reject all three. Use ray mapping and typed chronological input. Details of within-step contact order will be fixed by adversarial tests and recorded before acceptance.
