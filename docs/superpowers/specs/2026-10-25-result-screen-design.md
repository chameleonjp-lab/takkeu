# 結果画面・全登録順位の設計

ユーザーの第1〜第5段階の確定仕様を実装する。最新mainは `7b48f223b83c80b11ac9c242583577e9096d540f`（PR #25）。新規専用clone/ブランチで作業する。詳細な実装依頼を実行許可として扱い、段階ごとに検証してDraft PRでレビューを受ける。

## 既存の流れ
`createApp` が終了を検出 → `controller.finish` がplay/submission ID付きで保存 → finish RPC → idempotent submit RPC → TOP30更新。現在の状態通知は全再送キュー共通なので、個別結果の成功確認には使えない。ゲストは開始回数のみ送る。最終3D演出終了後に結果が現れる。

## 設計と選択
- コメントを独立した純粋関数へ。44個の開始値と文言、数字演出レベルを明示。境界は下限を含む。
- CSSで金属/虹色と登場演出。SVGを数字の前後に置き、乱数で枝分かれする短命なパスを生成。Canvasは軽いがDOMでの形状検証が難しく、Three.js変更は本体と負荷を共有するためSVGを選択。最大5本、約30fps、背面75%。画面非表示・非アクティブタブ・reduce motion・disposeで停止/解放。
- 個別送信通知にplay/submission IDを含める。別モジュールで結果の対象IDを保持し、その送信成功後のみ順位を取得。epochで古い応答を破棄。キューの既存再送は保持する。
- 追加RPCはtakkeu専用。既存 `get_best_score_ranking` の first_score non-null / ranking_status normal / game slug の条件と、スコア降順のcompetition rankを維持。全登録をサーバーで集計し、順位・総登録数・DB自己ベストのみ返す。除外登録は0行で明示的に扱う。既存テーブル・関数を変更しない。
- 集計単位は人ではなく登録名なので `○位 / ○登録中`、補足 `登録名ごとの自己ベスト順位`。TOP100は控えめなバッジ。
- 配置はスコア→コメント→順位→自己ベスト→操作→TOP30。44px以上の操作、通常テキスト、status通知、320px幅とiPhone 17 Pro相当の402×874を検証する。

## 非対象
ゲーム計算、音声、入力、送信契約、Xシェアの文言、TOP30を変更しない。mainへのmerge・公開はしない。実機Safari確認と自動WebKit検証は区別して報告する。
