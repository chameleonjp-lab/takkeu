# Takkeu visual extension architecture audit

Read-only source review, 2026-10-25. GitHub `main` tree: `aff31169fd6feaad7bad35f22fe3de26429296cf`. The local clones were still receiving files, so source was read through the connected GitHub plugin. No production files or external systems were changed.

## Main conclusion

The game already separates fixed-step simulation facts from Three.js presentation. New visual behavior for scores through 4000 can be driven entirely by `GameSnapshot.score`, `simTime`, immutable event facts and deterministic visual hashes. Leave collision, scheduling, speed, PRNG and ball rewards untouched. Event-position enrichment for losses is the one small domain change needed for effects attached to the actual lost ball.

## Simulation, score and event extension points

- `src/game/types.ts:6`: `GameEventKind` currently has player-hit, opponent-hit, ball-lost, milestone, smash-warning, game-over and table-bounce. `GameEvent` already provides optional `position`, `rallyScore`, `smashReturn` and two effect tags. `GameSnapshot` has `score`, `simTime`, `lostBallCount`, `celebrations`, paddles, live balls and progression. Snapshots copy nested values (`src/game/simulation.ts:37`). Rendering should never write these facts.
- `src/game/simulation.ts:60`: the internal `emit` gives every event an increasing per-run ID and copies its supplied position. Preserve this event ordering and identity.
- `src/game/simulation.ts:110`: a successful contact first captures the incoming plan's `smash`, increments score, updates rally celebrations, computes the interpolated paddle center and emits `player-hit` at the exact contact time. `position` is the paddle center at `z=config.paddleZ`, and `rallyScore` is the score after this hit. `action.position` separately contains the ball's actual contact center. The event is emitted before replacing its incoming plan.
- `src/game/simulation.ts:142`: loss currently marks the ball lost and emits `ball-lost` with only `ballId` and `time`, then increments `lostBallCount` and updates loss celebrations. Its precise position is missing. Compute a read-only point with `sampleReturn(ball.plan, ball.from, time)` at this exact loss branch (or when enqueuing the loss action), and pass it through the existing `emit` position argument. Do not use `ball.position`, which is the previous segment's position. Do not move the ball or consume randomness to compute the effect origin.
- `src/game/simulation.ts:146`: at 100 lost balls, game-over is emitted immediately and remaining actions stop. `src/game/simulation.ts:190` also ends a run when all balls are lost. Every lost ball is removed at line 195, so its origin cannot be recovered from the next snapshot.
- `src/game/simulation.ts:187`: only flying live balls receive a final sampled position. Lost balls are skipped. A segment that stops at loss still commits the original fixed interval; `stepSimulation` also commits `end` at line 243. Effects must use `event.time`, not assume it equals the final snapshot's `simTime`.
- `src/game/milestones.ts:2`: current presentation milestones stop at 555. Separate ball reward rules continue without a score cap; up to 30 balls are alive. `src/game/progression.ts:10` separates fixed visuals from reward crossings. New render thresholds can be resolved from `score` without changing this list or the reward counter. If adding state facts, keep them bounded rather than accumulating all hit/loss events.
- Existing simulation changes at 450 (smash), 520 (racket firework tag), 530 (bounce firework tag), and 555 (bounce deflection) are already implemented. Extending visual thresholds must not alter these or the functions in difficulty, flightSpeed, opponent, scheduler, collision, trajectory and targets.

## Time, pause and finish behavior

- `src/app/loop.ts:25`: only running sessions advance. Each `session.step(config.fixedDt, ...)` result is sent to `onEvents` immediately, then its events are accumulated for the next renderer frame. Pointer-driven flushes may therefore dispatch audio before drawing. Keep the renderer independent of these dispatch timings.
- `src/app/createApp.ts:95`: `onEvents` is exactly `events => audio.consume(events)`. Never route audio through `GameView.render`; resize/restore rendering receives empty events and must not replay sound.
- `src/app/finishPresentation.ts:5`: after game-over, the gameplay snapshot freezes. A cloned drawing snapshot advances only `simTime` by wall elapsed time until `celebrationEnd`; duration is capped at 5 seconds. Run changes and non-gameover phases reset it. Pause therefore freezes visual time; game-over continuation is intentionally a drawing-only clock.
- `src/app/createApp.ts:287`: RAF calls `loop.frame`, then `finishPresentation.frame`. On first gameover it commits ranking once, cancels input and records results. It keeps drawing while finishing and once after the finish ends; the frozen scene otherwise draws only on resize/restore or phase changes. The score/ranking/UI always use the actual simulation snapshot, while `view.render` receives the drawing snapshot.
- `src/app/createApp.ts:128`: resizing calls the same finish presentation clock and `view.render(..., [])`. `pause` draws one paused snapshot with empty events; context restoration recreates the view. Retry/home reset the session/run ID. New visuals need a run reset, deterministic reconstruction where possible, and a finish end time integrated with `celebrationEnd` if they must remain visible after the final loss.
- `src/render/particles.ts:33`: existing fireworks explicitly clear on both `ready` and `gameover`. They do not participate in the current drawing-only finish. Do not assume extending these particles alone will preserve a final-hit/loss effect after game-over.

## Renderer extension points and layering

- `src/render/createView.ts:16`: stable `GameView` API: optional prepare, render(snapshot,events), resize, inputMapping, setQuality, resources, dispose. Preserve callers and injected test views if extending it.
- `src/render/createView.ts:36`: create objects once, add the root, create bounded fireworks, and create celebration view with `objects.tableRig`. In `render` the order is `applyPresentation`, opponent update, fireworks update, celebration update, rim flash, render. A visual extension should own its resources and attach/update/dispose beside these systems, with a documented ordering if it overrides the existing part presentation.
- `src/render/objects.ts:65`: `parts` maps the individual self/opponent courts, floor, wall, structural frame, net and paddles. `tableRig` contains both court halves, court edges, net and structure. Environment floor/wall, player/opponent paddles, body and ball pool are outside `tableRig`.
- `src/render/presentation.ts:28`: `resolvePresentation` controls each part's visibility/rainbow state by applied milestones. At 490 the original opponent court/racket/body/floor/wall are hidden and a separate opponent field replaces the latter surfaces. At 500/510 motion becomes irregular. A new effect must honor these visibility gates so it cannot reveal unreleased opponent objects, especially balls, glows and shadows.
- `src/render/presentation.ts:59`: `applyPresentation` resets visible part materials every frame and positions the player paddle/balls, so changes made before this function may be overwritten. It also owns the ball visibility gate and glow/shadow state. Additive overlays are simpler to isolate; persistent material changes should be folded into the same presentation resolver/order.
- `src/render/field.ts`: opponent field is a separate shader on floor/wall, updated with drawing `simTime`, seeded visual motion and pulse. `resize` must update its screen-space resolution; preserve this for new shader surfaces.
- `src/render/celebrations.ts:50`: `tableRoot` is attached to `tableRig` while `worldRoot` is attached directly to scene. Existing loss lightning and digits move with the table; environment celebration is world-space. At line 112 this system writes tableRig.position and rotation every frame, and restores them in dispose. A new system must compose transforms, use a separate parent, or fold into this update; two independent writers will overwrite each other's shake/motion.
- Existing celebration draw order: environment 1, electric glow 4, electric 5, digit glow 6, digits 7. Existing batches are fixed buffers: net/electric quads, number quads and 48 environment quads. The numbers batch only reserves three digits per notice, which is appropriate to current loss notices (max 100); do not reuse unchanged for four-digit score notices.
- `src/render/particles.ts`: one ring of 1536 particles, fixed GPU buffers, 0.7 second lifetime, event ID deduplication bounded to 512 IDs, standard 24 vs low 12 particles per cue. Useful pattern for any new burst system. It ignores stale, future and foreign-run events.
- `src/render/createView.ts:46` and `src/render/prepare.ts`: reserve/reuse the ball pool and warm scene variants during loading. Allocate new GPU buffers/materials once, include shaders in preparation, and dispose all owned resources. `resources()` currently exposes geometry/texture/program/draw-call counts and existing particle stats; extending particle systems should keep diagnostics meaningful and stable after repeated retries.

## Existing celebration and audio behavior

- `src/game/celebrations.ts`: loss streak is consecutive losses no more than 2 simulation seconds apart; net burst lasts .9 seconds, shake begins at streak 4, special loss counts 55/77/88/99 alternate palette, tens display number notices. Repdigit scores enable edge electricity for 5 seconds; every positive century sets environment rainbow/gold flashing for 5 seconds. These facts currently use only timestamps/counters, with render-time shapes generated from deterministic hashes.
- `celebrationEnd` includes burst, repdigit, century and number notice deadlines. Extend it for any new finish-relevant state, without modifying game time or phase in presentation.
- `src/audio/audio.ts:89`: audio deduplicates by increasing event.time and event.id, enforces run ID, and ignores old events. player-hit uses rallyScore/smashReturn; every positive score divisible by 100 additionally creates one fanfare voice. Milestone events are not the trigger for fanfare.
- On `game-over`, audio clears ordinary voices but preserves fanfare tails. The app suspends audio after finish presentation; new finish durations should preserve this lifecycle instead of dispatching a second game-over or resetting audio.
- Voice limit is bounded at <=8; ordinary cues cannot interrupt fanfare. `setMuted`, suspend, reset and dispose clear voices. `tones.ts:20` uses audio-only deterministic noise, independent of simulation RNG. `playMilestoneFanfare` ignores score and lasts about 1.8 seconds; ordinary pitch progression saturates by score 35.

## Focused validation targets

Existing tests worth retaining/extending: `tests/unit/simulation-isolation.test.ts` already checks identical physics, event facts, PRNG and reservations under changed render frequency/muting; `finish-presentation.test.ts` checks frozen gameplay with continuing drawing time; `celebrations.test.ts`, `celebration-render.test.ts`, `presentation.test.ts`, `extended-render.test.ts`, `ball-instancing.test.ts`, `audio-fanfare.test.ts`, `loss-limit.test.ts` and `prepare-render.test.ts` cover the adjacent contracts. For added loss positions, verify event point at exact loss time without changing plan/score/PRNG/event order. For late visuals, test threshold boundaries through 4000, pause/retry/home/context restoration, game-over finishing, low quality, bounded GPU resources, and no hidden-side visibility leaks.
