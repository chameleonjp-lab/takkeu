# タッケウ：プレイ終了時の累計落球数を保存

実装日: 2026-10-27
対象: 名前を登録しランキングに参加するタッケウの各プレイ。ほかのゲームの順位・集計は変更しない。

## 目的

「何ラリー打ち返したか」だけでなく、プレイが終わった時点で「何球落としたか」を同じプレイIDに保存し、不自然な記録を調べる際に使えるようにする。

**重要:** タッケウの終了条件は「累計100球を落とす」だけではなく、「手元の球がすべてなくなる」場合も含まれる。したがってゲームオーバー＝100球とは扱わない。**コードの実際の `lostBallCount` を送る。**

## 新しい保存先

- `private.game_play_sessions.takkeu_final_lost_balls`: スコア送信前のゲーム終了処理で保存。**過去・旧クライアントの未報告はNULL** とし、0や100で埋めない。
- `public.score_runs.metadata.final_lost_balls`: 同じプレイのスコアが登録されたとき、サーバーが終了記録から自動的に転記する。スコアと確実にひも付ける。
- プレイの同定には名前だけでなく既存の `play_id` を使う。名前だけでは同名ユーザーを区別できない。
- 記録値は0〜100の整数。リタイアや準備中止も0〜100で扱い、事実でない100球を補わない。

## 送信の手順

新しいクライアントはゲーム終了時（game_over）・ホームへ戻る時（retire）にスナップショットの `score` と `lostBallCount` を同時に控える。スコア再送待ちのデータにも同じ値を保持する。

`finish_takkeu_play_v2` が既存の `finish_game_play_v1` を呼び、既存のプレイ時間上限・スコア照合・二重終了判定をそのまま使う。成功した同じデータベース処理内で落球数を保存する。スコア提出はこれまでの `submit_score_idempotent_v1` を使い続ける。

- 再送は同じ `play_id` と落球数なら受理する。同じプレイIDで異なる落球数は拒否する。
- 終了前の途中経過に記録された累計落球数より、終了時の累計落球数が小さい場合は拒否する。
- 旧バージョンの再送待ちデータには落球数が存在しない。従来の終了処理に送って、NULLのまま保存する。
- 名前なしのプレイは引き続きランキングに送らず、開始回数だけを記録する。匿名プレイの終了時落球数は今回の範囲外。

## 調査用読み取りSQL（個人を特定する通信記録は不要）

```sql
select
  r.id as run_id, r.normalized_name, r.score, r.created_at,
  s.result_type, s.started_at, s.finished_at,
  s.takkeu_final_lost_balls,
  (r.metadata ->> 'final_lost_balls')::integer as submitted_final_lost_balls
from public.score_runs r
join private.game_play_sessions s on s.play_id = r.play_id
where r.game_slug = 'takkeu'
order by r.created_at desc
limit 50;
```

同じ記録でも終了時落球数が未報告ならNULLとなる。過去の11,354ラリーの記録について、今回の変更だけで落球数が判明するわけではない。

## 限界と検証

落球数もブラウザから送られるため、単独ではBOTを確定できない。スコア、サーバー計測のプレイ時間、途中経過との整合性を組み合わせて審査する。

- テスト: 初期状態、累計100球未満の全滅終了、異常値、同じ送信の再試行、別値の二重提出、過去のNULL保持、既存ランキング送信との両立。
- 本番データベースの追加機能は公開サイトより先に導入可能で、未更新の既存クライアントは従来の処理を維持する。
